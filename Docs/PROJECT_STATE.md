## Founder recap

Veliora is intended to help freight dispatch companies manage their fleet, search
load boards, rank opportunities, review promising loads, and record outcomes.
Dispatchers use company workspaces; admins manage access. The code still uses the
names “AI-Assisted Dispatching” and “Freight Command Center”; “Veliora” is the
founder's product name used here.

There is a substantial local MVP foundation: a Next.js frontend, FastAPI backend,
17 database models, and migrations. Local checks verified registration/login,
company and fleet creation, simulated truck searches, ranking, and saving/clearing
loads into a dispatcher work queue. This is not yet a complete operational freight
product. Every searched load is generated by a mock worker. Real board access,
broker communication, the booking UI, assignment/completion, and AI display are
unfinished. Attractive screens and “autonomous” labels overstate current behavior.

The latest meaningful implementation connected dispatcher actions to the frontend
and prepared Live Loads as a saved/contacted queue. The next discussion should
resolve the intended complete user journey and real data access before expanding
the product surface.

The current core flow is:

```text
Register/login -> bearer token -> select/create company -> create driver/truck
  -> POST /searches/start (truck defaults + overrides)
  -> SearchBatch -> TruckSearchSession -> background mock worker
  -> company-scoped Load + observations in LoadSnapshot + LoadSource + WorkerLog
  -> GET /scores calculates/persists dispatcher ranking -> ranked frontend table
  -> save/reject/favorite/contacted/clear-action -> DispatcherAction history
  -> latest save/contacted actions -> current dispatcher's Live Loads queue

Separate backend paths:
existing scores -> POST AI explanations -> Gemini -> saved explanation
selected snapshot -> booking API -> BookedLoad -> manual status updates
```

## Dispatch workflow and integration boundaries

Company records currently hold an ID and name. Trucks/drivers belong to that
company; there is no separate carrier profile with MC/DOT/insurance/onboarding
documents. A truck's human-facing `truck_id` differs from its integer database `id`.
The frontend “tracker” updates ordinary status/location/notes manually.

Search accepts database truck IDs, freezes truck defaults plus optional overrides,
and blocks statuses other than `available`. The mock generator creates five loads
per session, seeded by session ID, with synthetic lanes, rates, dates, contacts,
and `mock-load-board.local` source URLs. It uses equipment and active board names
(or default board names); it does not enforce the stored min RPM, weight,
deadhead, location, availability date, or preferred-source filters. Setting an
unreachable RPM and a one-pound maximum still returned five generated results in
the disposable check. Ranking uses dispatcher preferences rather than the truck's
filter snapshot, so two trucks do not automatically receive suitability-aware
rankings. [Generator](../Backend/app/workers/mock_search_worker.py),
[filter builder](../Backend/app/services/search_service.py),
[scoring inputs](../Backend/app/services/scoring_service.py).

Board “check-health” stores a caller-supplied assessment; it does not connect to a
board. Real integrations will require choosing an authorized access method,
obtaining the appropriate account/API permissions or approvals, credentials, and
implementing/testing the provider. No live-board access or approval was established
by this review. [check_load_board_session_health](../Backend/app/services/load_board_service.py).

Save/contacted are workflow markers, not proof of broker communication or booking.
Favorites do not enter Live Loads, and changing from save to favorite removes that
item from the queue. Only the current dispatcher's actions are listed, grouped by
session/load, so the same stable load can recur across sessions. The UI shows at
most 18 queue rows, has no pagination, and fetches on company change/mount rather
than subscribing to updates. Claim/watch/hide/call handlers in the workspace store
are no-ops; assignment has an empty driver list and TODO callback.
[list_live_load_actions](../Backend/app/services/dispatcher_action_service.py),
[LiveLoadsPage/toLiveActionLoad](../frontend/features/dispatch/operational-screens.tsx).

The AI integration is a direct `generateContent` request to Google's API with the
model string `gemini-3-flash-preview`, a 50-second client timeout, temperature 0.3,
and a 512-token output budget. These are repository settings, not a claim that the
model is currently available. The prompt asks for two practical sentences using
load/ranking data. Results are plain text; validation mainly checks length and
terminal punctuation, not factual correctness or a structured schema. Generation
defaults to five existing scored loads (API limit 1–20); scoring does not call AI.
Failures can return an empty successful response, so HTTP 200 does not prove an
explanation was produced. The cache includes snapshot, score, breakdown, and prompt
version, scoped by company/dispatcher. The stored-list endpoint does not recheck
current hashes, so old explanations may remain after rescoring. No real provider
calls were made. [GeminiClient](../Backend/app/services/llm/gemini_client.py),
[AIExplanationService](../Backend/app/services/ai_explanation_service.py),
[AI routes](../Backend/app/api/v1/scoring.py).

## Data, migrations, and configuration

The 17 modeled tables form these groups:

| Group | Entities and relationships |
| --- | --- |
| Identity/company | `users` connect to `companies` through `company_memberships` with role/status. |
| Fleet/integrations | Company-owned `drivers`, `trucks` (optional current driver), and `load_board_sessions` (metadata only). |
| Search | Company/creator `search_batches` have truck/owner `truck_search_sessions`; sessions have `worker_logs`, JSON filter snapshots, timing/status, and `is_hidden`. |
| Results | Company-scoped `loads` have many `load_snapshots` and `load_sources`. Sources also reference the specific snapshot/session and hold source/contact details. |
| Decisions/outcomes | `dispatcher_actions` reference company, dispatcher, session, load, and snapshot. `booked_loads` additionally link truck/optional driver and copy booking-time details. |
| Ranking/AI | `scoring_preferences` are unique per company/dispatcher; `scoring_results` per dispatcher/snapshot; `ai_explanations` per company/dispatcher/input hash. |

Actual IDs are integers and flexible payloads use SQLAlchemy JSON; the historical
UUID/JSONB recommendations are not the implemented schema. Some early models
(users, companies, memberships, trucks, drivers) lack the standard timestamps
proposed in design docs. [models/](../Backend/app/models/).

There are 12 migrations in one chain, from `386e8b67a005` to
`b82f6e4d9a12`. The second “create core tables” revision, `54822fd38e7a`, is a no-op,
not a second table-creation attempt. The last two add expanded truck defaults and
session hiding. The chain and PostgreSQL SQL generation passed offline. The
applied revision of any existing database is unknown; no live database was queried
or migrated. Tests create current model metadata directly and therefore do not
validate Alembic upgrades. [migration versions](../Backend/alembic/versions/).

Persistence gaps: no operational assignments, broker profiles/interactions,
notifications, settings, or telemetry tables/services; no durable job recovery or

## Confirmed gaps and risks

1. **Tracked credential material and migration-target mismatch.**
   `Backend/alembic.ini` contains a password-bearing database URL, and migration
   `env.py` uses it independently of application settings. Credential validity and
   reuse are unknown; treat the value as exposed, rotate if applicable, and decide
   how to remove it from configuration/history. Values are intentionally omitted
   here. Configuration changes were outside this documentation-only task.
   [alembic.ini](../Backend/alembic.ini), [env.py](../Backend/alembic/env.py).
2. **Cancellation does not cancel execution; timeout is only metadata.**
   `cancel_truck_search_session` writes a status, but the manager/worker checks
   neither cancellation nor elapsed timeout before running/finishing. A canceled
   pending session became completed in the disposable reproduction. The cancel
   and clear routes require company membership, without the owner check applied
   to load actions. [search_service.py](../Backend/app/services/search_service.py),
   [searches.py](../Backend/app/api/v1/searches.py),
   [WorkerManager](../Backend/app/workers/worker_manager.py).
3. **An admin can leave a company with no active admin.**
   Self-removal reproduced this. `update_membership` likewise lacks a final-admin
   guard; role/status inputs are unrestricted strings. Historical endpoint plans
   claiming a safeguard are not implemented. [membership_service.py](../Backend/app/services/membership_service.py),
   [membership schema](../Backend/app/schemas/membership.py).
4. **Visible operational controls can do nothing or mislead.**
   Workspace claim/watch/hide/call/accept/reject and notification producers are
   no-ops; this is separate from the functional ranked-table action API.
   Assignment/completion are TODOs, settings show a saved timestamp without
   persistence, global command results always return `[]`, and Live Loads sets
   `aiScore: 0` rather than loading an AI result. [workspace-store.ts](../frontend/store/workspace-store.ts),
   [operational-screens.tsx](../frontend/features/dispatch/operational-screens.tsx),
   [topbar.tsx](../frontend/components/layout/topbar.tsx).
5. **Search history depends on local browser IDs.**
   Only 12 batch IDs are retained in an unpartitioned localStorage key; the UI
   lacks server-side company history discovery and does not filter retrieved
   batches by active company. A user with access to multiple companies can have
   mixed history displayed; API membership checks still deny unauthorized company
   access. Rejected fetches are discarded by `Promise.allSettled`, potentially
   pruning stored history on transient failures. Browser reproduction remains to
   be done. [SearchControlCenter/refreshBatches](../frontend/features/search/search-control-center.tsx).
6. **Load identity does not reliably preserve changing-rate history.**
   The dedup key includes rate and weight, but excludes pickup date and external
   load ID. A changed rate can become a different stable Load, and otherwise
   identical shipments on different days can merge. This is a confirmed property
   of the key; business impact with real data is unmeasured.
   [build_load_deduplication_key](../Backend/app/utils/deduplication.py).
7. **Authentication/realtime need production hardening.**
   Tokens are stored in localStorage and WebSocket tokens are query parameters;
   URL logging or script compromise can expose them. Subscription authorization
   happens at connect time with no later expiry/membership recheck. This review
   establishes code behavior, not a demonstrated exploit. [api-client.ts](../frontend/api/api-client.ts),
   [websockets.py](../Backend/app/api/v1/websockets.py).

Additional source-supported reliability risks, not concurrency-tested: active
search/truck-number/booking duplicate checks are query-then-insert without matching
database uniqueness guarantees; workers have no durable restart recovery; booking
status updates do not enforce lifecycle transitions or synchronize fleet capacity;
company creation commits the company and initial membership separately; worker
failure handling does not roll back a failed database transaction before writing
its failure state. The WebSocket manager is process-local and its synchronous
broadcast bridge only runs from a suitable AnyIO worker thread.
[models/](../Backend/app/models/), [company_service.py](../Backend/app/services/company_service.py),
[booking_service.py](../Backend/app/services/booking_service.py),
[mock_search_worker.py](../Backend/app/workers/mock_search_worker.py),
[connection_manager.py](../Backend/app/websockets/connection_manager.py).
